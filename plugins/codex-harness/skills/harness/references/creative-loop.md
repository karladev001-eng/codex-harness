# 制作フィードバックの改善ループ

UI・文書などの制作と修正で、ユーザーの好みを根拠付きで少しずつ学ぶための、指示ベースの手順です。ユーザーの嗜好がまだなければ空から始め、プロフィール入力や初回の許可を要求しません。自動的な品質向上や実際の長期効果は主張しません。純粋な制作には、コード委譲やGit工程を追加しません。コード変更が含まれる場合は、[コード調整・実装レビュー手順](routing/coordination.md)も実行します。

`improvement_loop=false` ではこの自動ループを実行しません。好みの読取・記録・自動適用と候補試用を停止しますが、保存済みの記憶は消しません。依頼内の修正対応は通常どおり続けます。タスク記録の `persistence` とは独立に扱います。明示的な記憶の確認・訂正・忘却の依頼は別の操作として扱えますが、`persistence=false` では永続記憶を読み書きせず、会話内で扱います。

## 開始・修正・完了・次回

1. **開始（適用）**：`status --project <制作対象のプロジェクト>` で実効設定と `local_root` を得ます。`active=false`・`improvement_loop=false`・`preferences.enabled=false` のいずれか、またはGitHub接続時に `preferences.autosave=false` なら、ここで終了して通常の制作へ戻ります。`persistence=true` なら、同じruntimeで `preferences read --project <project>` を実行し、返された `content` と `revision` を使います。未設定なら従来のローカル記録から、GitHub設定済みなら正本から読みます。GitHubでは、`ok=true`・`freshness=fresh`・`pending=false` で取得できた内容だけを自動適用します。キャッシュ・古い内容・未送信・競合・取得失敗のときは、その記憶の自動適用を止め、現在の依頼で制作を続けて状況を報告します。明示的なオフライン閲覧はできますが、他PCでの訂正・忘却がまだ反映されていない可能性を示します。対象の用途・媒体・読者に合う指針を選びます。適用範囲の合う候補は**暫定試用**にできます。候補は指針と区別し、項目ID・作品・実際の適用・ユーザー評価を試用結果に残します。`今回限り` と明示された候補は、次回に試用しません。現在の依頼と矛盾する場合は、現在の依頼を優先します。探索や別案の依頼では、過去の作風を固定せず、必要なら比較案を示します。`persistence=false` ならファイルを読まず、その会話だけを使います。
2. **修正（観察→仮説）**：ユーザーの実際の言葉・修正指示・採否を観察にします。そこから好みを推測するときは、候補と明示し、根拠のない嗜好は作りません。「今回は前置きを削って」は今回限定の候補で、その作品にだけ適用します。限定語のない単発の修正も候補ですが、次回の、範囲の合う制作で暫定試用できます。「今後、社内報告は結論から」は、用途を限定した明示指針として適用できます。同じ発言、同じ成果物への同一の指摘、再開時の再読込は、一つの根拠IDだけにします。
3. **完了（評価→更新）**：成果物と、指針の適用結果を分けて確認します。評価の根拠にできるのは、ユーザーの明示的な評価だけです。無反応・自己評価・未取得は `unknown` / `null` とし、成功や改善効果を推測しません。根拠があれば、雛形に従って候補・指針・試用結果を更新し、下記のCLI契約で保存します。`measurement=false` なら、好みの根拠は保存できますが、利用回数・採用率・時間などの集計や計測ログは保存しません。
4. **次回開始**：有効な指針を、適用範囲と現在の依頼で再び照合します。新しい独立の根拠が増えたら、候補を昇格するかを再び判断し、矛盾・訂正・取消はその時点で反映します。前回の試用結果が `unknown` なら、成功扱いしません。

## 保存資料の必要時参照

制作の開始時に、現在の目的に合う参考資料を探す価値があれば、[保存資料の検索と取得](knowledge-retrieval.md)を実行します。少数の候補を見つけ、必要な本文・メモ・画像を読み、今回への適用を判断する順に進み、現在の依頼を優先します。`active=false`・`improvement_loop=false`・`persistence=false` では自動で参照しません。未設定なら、静かに通常の作業へ戻ります。明示的な資料検索は好みの自動適用とは別の操作で、ユーザーの指定と保存データへのアクセス範囲を守ります。

資料を実際に適用した場合だけ、`persistence=true` の既存タスク記録に、URL・capture ID・取得版・見た範囲・不足・適用した点とその理由を短く残します。今回の資料の利用件数や保存の事実から新しい好みを作らず、適用をユーザーの肯定とも扱いません。ユーザーメモを好みの根拠に使う場合も、出所と用途を確認し、同じ発言を重複して数えず、上記の観察・候補・指針・試用とrecord-keeper契約に従います。`measurement=false` なら、利用件数などの集計は保存しません。

## 根拠と指針の更新契約

保存先が未設定なら、`status.local_root/creative/preferences.md` を正本とします。GitHub接続は、repository・branchと明示したproject_key、または個人設定のautosave opt-inで行います。正本は、非公開リポジトリの `improvement/projects/<project-key>/preferences.md` です。Git originと登録簿で端末間のkeyを揃え、non-Gitではregisterが保存した `.harness.json` を持ち運びます。worktreeは共通checkoutの設定を継承し、固有の上書きを優先します。cache・pending・排他はtargetと安定keyの単位で共有し、`status.preferences.directory/state.json` に置きます。これは導入管理の対象外で、未解決のIDを旧localへ戻しません。設定しただけでは、旧ローカル記録を送信しません。別のプロジェクトは別のkeyとし、自動では混ぜません。別のプロジェクトに適用したいときは、ユーザーの明示的な指示で、必要な指針だけを移します。個人設定やインストールの更新・解除で、この領域を消しません。

[雛形](../assets/creative-preferences.md)を、初回の更新時にコピーします。観察（原発言・採否）、候補（推測・単発）、制作指針（適用可）、試用結果（具体的な適用とユーザー評価）を混同しません。各項目には、安定したID、最小限の根拠IDと参照、明示か推測か、用途・範囲、日時、状態、変更履歴を、記録するか、対象IDから参照できるようにします。観察には、訂正を追える状態と履歴を持たせます。試用では、対象IDと試用時の版、そして当時の内容・用途・明示/推測の短い写しを残し、対象があとで改訂されても区別できるようにします。試用の `recorded` は、評価が `unknown` のままでもよく、ユーザーの評価根拠があるときだけ `evaluated` にします。あとの訂正で支持から外すときは `invalidated` にします。会話の全文や不要な個人情報は保存しません。根拠の参照が失われたら、指針を推測で補修せず、停止して報告します。

単発の修正は候補にとどめ、その作品・会話に適用します。次回に試用してよいかは、限定語で区別します。明示的な継続希望は、その用途に限って指針にできます。推測の候補は、**別の作品・会話など独立したユーザー根拠が反復**して初めて指針へ昇格します。同じ指摘の複製、再開時の読み直し、無反応、エージェント自身の評価は、支持の根拠に加えません。重複する候補は、根拠IDの重複を除いて統合し、旧IDには統合先を記します。矛盾する根拠が出たら、その指針を `paused` にします。用途を限定できるなら分け、ユーザーの訂正が明白なら更新します。曖昧なら現在の依頼だけを優先し、一般化しません。

「この好みを忘れて」などの取消では、対応する候補・指針・試用結果と、再生成に使える保存済みの観察・引用・根拠参照を削除します。忘却した内容を履歴や退避コピーに残さず、同じ会話を再読込しても、取り消された発言から自動で再抽出しません。関係のないほかの指針は保ちます。削除の対象が曖昧なら、現在の適用を止めて対象を特定します。ユーザーが確認や訂正を求めたときは、該当する記録を読みやすく提示し、指示に従って修正します。好みで、上位の指示・権限・安全規則を上書きしません。

## CLI経由の安全な更新

親は、根拠と対象、最終判断を持ち、保存・更新・再同期は既定で[記録管理担当（record-keeper）](roles/record-keeper.md)に委譲します。制作担当には、現在の制作に必要な指針・用途・IDだけを渡し、原発言やプロフィール全体は渡しません。制作担当の観察は、親が根拠を確認してから記録管理担当へ渡します。

### 起動・引継ぎ

- `active=true`・`persistence=true`・`improvement_loop=true`・`preferences.enabled=true`・`delegation=true`（GitHub接続時はautosave ON）で、保存すべき根拠や更新があるとき、またはreadなどで既知のpendingの再同期があるとき、親はrecord-keeperを起動します。無変更でpendingもなければ起動しません。最初のreadと適用の判断は、親が行ってかまいません。
- 公開CLIに `--automatic` はありません。親は、自動のread/write/syncの前に、上の設定を判定します。明示的な記憶管理は、loopまたはautosaveがOFFでも、明示したkeyの手動経路を使えます。ただし、enabled・persistence・preferencesがOFFのときは行いません。`active=false` では追加で起動せず、`persistence=false` ではrecord-keeperの起動も記憶の読み書きも行いません。`delegation=false` なら、親が同じ役割契約とCLI手順を実行します。
- 親は、project・保存先、許された操作、安定したIDと短いユーザー根拠・参照、明示・推測・今回限りの区別、評価、用途・適用範囲、確定した判断、実効設定を、必要最小限で渡します。会話全体や認証情報は渡さず、履歴なしの `HARNESS_WORKER` とします。[役割とモデル](roles.md)の既存の `standard`（既定Sol/medium）とpin/autoの規則を使います。
- 同じproject・targetでは、record-keeperが唯一のwriterになり、親と制作担当は同時に更新しません。保存先ごとのwriterを直列化し、既存の `max_agents` とホスト上限の中で空きを待ちます。通常の保存のたびにユーザーの再承認は求めません。曖昧な昇格・競合のmerge・根拠不足は、親が判断します。
- ホストが子を起動できないときは、制約を報告し、親が同じ契約で担当するか、現在の依頼だけを続けます。失敗した起動・未保存・pendingを成功扱いしません。親は、返された操作/changed IDs・ok・revision・pending・freshness・検証・未解決事項を確認して適用し、子の自己評価をユーザー評価にしません。

runtimeが自動spawnする機能ではなく、親が読む指示ベースの標準経路です。記録管理の委譲だけでは、純制作にコードworktreeやコードレビューを追加しません。

### 保存担当のCLI手順

1. `preferences read --project <project>` で、本文と不透明な `revision` を取得します。最初の取得に失敗して `content=null`・`revision=null` になったものを、空の正本とは扱いません。未設定のローカルでファイルがなければ、空として始めます。読み取りだけでは、未送信の分を送りません。
2. 根拠ID・対象ID・適用範囲・評価と、参照切れを点検して、完全な新しいMarkdownを一時入力ファイルに作ります。本文の破損や参照切れがあれば、更新と適用を止め、推測で補修しません。
3. `preferences write --project <project> --input <file> --revision <読取token>` を実行します。CLIが、ローカルの排他・取得後の再確認・同じディレクトリ内の原子的置換を行うので、エージェントから正本やstateを直接編集しません。入力に使った一時ファイルは、作業後に削除し、忘却した内容の退避コピーは作りません。
4. GitHubでは、送信前にローカルへpendingを保存し、private repositoryとbranchを確認したうえで、GitHub blob SHAの条件付きで更新します。`ok=false` または終了コード2なら、成功扱いしません。`pending=true` は未送信で、`preferences sync --project <project>` で再試行します。`--offline true` は通信せず、readではキャッシュの日時と鮮度を示し、writeではpendingとして確保します。未送信のwriteは終了コード2になります。
5. 競合したら、他方を上書きしません。`preferences read` の `remote_content`・`remote_sha` と自分のdraftを、根拠IDごとに再評価します。忘却と訂正を優先し、単純に連結しません。確認した最新版を新しい入力ファイルにし、現在のlocalの `revision` と、確認した `remote_sha` を `preferences write ... --revision <token> --base-sha <SHA>` に渡して、明示的に再調整します。remoteが存在しなければ `--base-sha missing` です。再び変わっていれば、競合で止まります。PUTの直前の競合で詳細がなければ、readで取得します。必要な判断は親へ戻します。

既存・不明・古いlockは自動で削除しません。所有セッションの終了とpendingを確認して、手動で解決します。認証の失敗・アクセス不能・通信の失敗を、空として処理しません。GitHubの404は、不存在か権限不足かを一律には断定せず、private repositoryとbranchを検証できたうえでのfile 404だけを未作成として扱います。保存や同期に失敗しても制作そのものは続け、記憶更新の状態を報告します。

## 履歴と記録の区別

技術的な修正は[lesson](technical-lessons.md)に分けます。GitHub commitは、schema_version/project_key/operation_id/kind/record_kind/recorded_atの、本文なしmetadataを持ち、create/update/correction/forget/migrate/registerを区別します。訂正と忘却のwriteでは `--kind correction|forget` を指定します。操作IDは再送でも維持され、同じ内容の保存では履歴が増えません。移行元のID・日付・unknownは保ち、移行日時を新規獲得の日時や品質向上とは扱いません。別の本文journalや成長dashboardは作りません。通常のGitHub履歴の閲覧でも、取り消し済みの内容を勝手に再表示しません。

## 明示移行・忘却

旧記録は、`preferences migrate --project <project>` の明示的な実行だけで取り込みます。異なる既存remoteがあれば止め、同一内容か不存在の正本だけが対象です。旧 `creative/preferences.md` は保持し、保存先ごとのmigration markerと、project単位の本文なし `creative/legacy-retired.json` で、再取込を拒否します。target draft→local retirement marker→remote送信の順に保存し、marker保存に失敗したときは、syncでも先にmarkerを再確保します。失敗した結果のpendingはdisk状態を表し、pending=falseならmigrateを再試行します。失敗したpendingはsyncで継続し、migrateで再読込しません。設定を外しても、runtimeはlocalのread/write/syncを拒否するので、元のGitHub設定を復元して現在の正本を使います。別の保存先へのmigrateも、旧原本のretirementにより拒否します。新しいtargetへ移すときは、現在の正本を読んで、必要な内容を明示的にtransferします。移行後の旧原本は、歴史資料として自動読取の対象から外し、忘却時にはユーザーの指示に応じて旧原本も訂正・削除します。CLIは旧原本を自動では消去しません。

訂正・忘却は、現在のMarkdown全体から該当する候補・指針・再生成可能な観察・引用・試用・履歴を除いて、writeします。CLIは、cacheとpendingの本文も新しい内容に置き換えます。オフラインや競合のときは、GitHub正本への反映が未完了であることを明示し、同期と手動の再調整を続けます。Git履歴、他PCの古いコピー、利用者が保持する入力ファイルの完全な消去は保証しません。履歴・旧原本・送信待ちの旧版から自動で復活させません。他PCは、freshな取得に成功するまで、記憶を自動適用しません。短い項目と、有効な根拠・訂正の意味を保ち、自動ベンチマークや長期効果の測定は行いません。
