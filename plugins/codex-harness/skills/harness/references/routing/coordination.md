# 調整手順

コード変更では開始時と完了時に[技術的な修正の再利用・記録](../technical-lessons.md)を実行する。少数のfreshなlessonを必要時だけ照合し、根拠のある修正だけを記録する。調査の委譲だけならこの追加手順は不要。

1. [事前提示・承認](preimplementation.md#実装前の説明仕様視覚モック)を満たし、目的・対象外・番号付き受入条件を確定する。利用可能ならHTML計画スキルで仕様正本に対応する対話型HTMLを作る。場所はソースcheckoutの `authoring-skills/codex-html-plan/SKILL.md`、導入済みでは本スキル同階層の同パス、独立導入では `.agents/skills/codex-html-plan/SKILL.md`。なくても提示・仕様・UIモック要件は残る。[パケット雛形](../../assets/task.md)に担当範囲・依存・仕様版・コミット済み基点・資料・未解決事項を記す。探索は大きい場合だけ委譲。文献探索は[探索](../roles/paper-discovery.md)で範囲/停止条件を分け、候補確認は[資料確認](../roles/source-verification.md)へ。親がID重複を除き発見数と検証数を別集計する。
2. 保存ONは必要記録だけ `docs/harness/` へ。主要入口/検証は[案内](../../assets/project-map.md)、後に影響する判断は[ADR](../../assets/adr.md)。全ファイル一覧・会話全文は作らない。
3. 依存の欠落/循環を解消しreadyだけ並列実行。実装/制作は提示・承認・必須判断の充足を確認し、準備の調査/仕様/モックは妨げない。実装・調査・レビュー・統合・外部相談の同時枠は `max_agents`（既定3）とホスト上限の小さい方以下。[並列規則](../parallel.md)を守る。
4. [役割・モデル](../roles.md)で作業の性質からモデル、必要品質からeffortを別に選ぶ。メインのモデルはホスト現在値で変更できない。開始時/各子起動時に実効設定・pin由来・明示指定と、実際の起動面の候補/対応effortを確認。取得元・選択根拠・実model/effortを記録（保存OFFは会話内）。履歴なし方式（Codexは `fork_turns="none"`、Claude Codeは役割を指定した通常起動。[ホスト別](../hosts/codex.md)）を明示。利用不能なら報告し、別モデル/全履歴へ黙って代替しない。
5. 子へ `HARNESS_WORKER`、役割、パケット、役割参照の絶対パス、cwd、実効設定、必要資料だけを渡す。未コミットのパケットは子worktreeにないためインラインか親checkoutの絶対パスを使う。実効設定は親から渡し子の基点で再解決させない。インラインでも受入条件、資料参照/版/提示証拠、承認範囲/ユーザー発言根拠を省略せず担当受領時に確認。別タスクは新しい子、同じ修正は同じ子を継続可。子の再委譲は禁止。
6. review ONは実装者と別の担当に[独立レビュー](../reviewer.md)を委譲し、実差分・コードを読ませる。コードは[コードレビュー](../roles/code-review.md)、Web画面評価の受入条件とブラウザがある場合だけ[画面評価](../roles/web-review.md)も適用。修正/再レビューは最大2巡。残れば親が仕様/方針を判断し完了にしない。
7. 承認済み変更は統合担当へ渡し、依存順に統合・結合検証。review ONは最終の変更間整合性も独立レビュー。親は統合コードを代筆しない（delegation OFFを除く）。
8. 修正記録の有無と理由、保存した場合のok・終了コード・pending・freshnessを確認し、未保存・未送信を完了扱いしない。最新仕様/コード版の受入条件と必要レビューPASSを確認。結果・変更パス・検証証拠・未解決事項・commit IDを返す。仕様改訂の影響結果と依存統合は再検証する。
