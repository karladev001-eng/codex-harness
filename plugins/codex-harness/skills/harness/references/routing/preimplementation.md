# 実装前の説明・仕様・視覚モック

activeな実装・制作・修正では、delegation/review/loopのON/OFFに関わらず、次の提示と承認を**本実装・担当への着手指示・production組込みより先に**済ませます。小変更なら短くしてよいですが、免除しない。inactiveでは追加しません。純調査・仕様作成・発案・相談・批評だけに、本実装・承認・コード委譲・Git工程を付加しない。相談は[外部相談の判定](peer-consult.md)へ進め、あとで実装する範囲にはこの手順を適用します。

1. **仕様**：何を作る・変えるのかを説明し、目的、対象内外、利用者から見た振る舞い、入出力・異常時、番号付き受入条件、制約と未解決事項を示します。入出力や異常時が当てはまらなければ、非該当なら理由を書きます。既存の仕様やモックは、今回の依頼に合うか確かめてから再利用できます。
2. **UIモック**：UIがある場合は、主要画面・操作・必要状態を目で確かめられる画像・ワイヤーフレーム・表示できるHTMLなどを作り、仕様版と対応させて、表示か閲覧参照を提示します。説明文だけは不可です。調査・仕様・モックは準備として進められるが、実機能・production組込みは先行しない。
3. **承認**：必要資料の提示後、その仕様版・範囲へのユーザー本人の明示承認まで開始しない。未解決0件でも必要です。沈黙・経過時間・未操作の既定値・質問回答だけ・提示前の一般依頼は承認でない。提示できない制約があれば明示します。回答と承認は別欄・別記録にし、同じ発言に両方が明示されれば各々記録します。同じ提示版・範囲の既承認は再取得しない。上位・ユーザーの指示と権限の制約は守ります。
4. **未解決と範囲**：確定仕様・承認とは別欄に、影響範囲、選択肢や提案、必要な判断とその担当を書きます（0件なら「なし」）。承認だけで実装必須判断を補完せず、解決・明示除外・ユーザーの判断委任まで影響範囲を止める。大きな実装では、個別に着手する前に、全体目的、主要な機能・画面・流れ、対象内外、構成/依存、段階の概要を示して承認を得ます。部分承認ならその範囲だけを始め、子には親仕様版・承認範囲・根拠を渡します。単なる分割、承認内の通常検証・修正は再承認不要です。
5. **改訂**：振る舞い/UI/範囲/重要設計を変えるときは、影響範囲を止め、説明・仕様・モックを更新して再提示・再承認を得ます。誤字など意味不変の修正なら承認範囲を維持し、差分を記録します。影響を受けた結果は再検証します。

## 記録

正本は既存のタスク仕様パケット（`docs/harness/tasks/<id>.md`、または既存CLIの `<id>.json`。[雛形](../../assets/task.md)）で、重複した仕様は作りません。資料の参照と版、提示証拠（会話の位置・表示先など）、UIが非該当の理由、制約を書きます。独立した承認欄には状態・仕様版・範囲・ユーザー発言の根拠を、未解決欄には判断への回答を書きます。

承認待ちはplanned/承認pendingです。readyには提示・承認と、実装必須判断の解決・明示除外・委任が必要です。新enum/schemaは増やさず、既存の自由欄などを使います。保存OFFでは、同じ内容を会話内で提示・記録し、インライン引継ぎします。

ready移行・担当受領・レビューのたびに、現在の仕様版と承認範囲・根拠が一致するか確かめます。不足/不一致があれば担当から親へ戻し、着手しない。改訂したら資料・提示証拠・承認欄を更新し、完了時は最新版の受入条件と提示・承認の証拠を確認します。
