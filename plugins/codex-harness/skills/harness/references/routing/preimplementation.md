# 実装前の説明・仕様・視覚モック

activeな実装・制作・修正は、delegation/review/loopのON/OFFに関わらず、次の提示と承認を**本実装・担当への着手指示・production組込みより先に**満たす。小変更は短くできるが免除しない。inactiveには追加しない。純調査・仕様作成・発案・相談・批評だけに本実装・承認・コード委譲・Git工程を付加しない。相談は[外部相談の判定](peer-consult.md)へ進め、後に実装する範囲には本手順を適用する。

1. **仕様**：何を作成/変更するか説明し、目的、対象内外、利用者の振る舞い、入出力・異常時、番号付き受入条件、制約・未解決事項を示す。入出力/異常時が非該当なら理由を記す。既存仕様・モックは現依頼との適合を確認して再利用できる。
2. **UIモック**：UIがある場合は、主要画面・操作・必要状態を視覚で確認できる画像/ワイヤーフレーム/表示可能HTML等を作り、仕様版と対応させ、表示か閲覧参照を提示する。説明文だけは不可。調査・仕様・モックは準備として進められるが、実機能・production組込みは先行しない。
3. **承認**：必要資料の提示後、その仕様版・範囲へのユーザー本人の明示承認まで開始しない。未解決0件でも必要。沈黙・経過時間・未操作の既定値・質問回答だけ・提示前の一般依頼は承認でない。提示不能の制約を明示する。回答と承認は別欄・別記録とし、同じ発言に両方が明示されれば各々記録する。同じ提示版・範囲の既承認は再取得しない。上位/ユーザー指示と権限制約を守る。
4. **未解決と範囲**：確定仕様・承認とは別欄に、影響範囲、選択肢/提案、必要判断と担当を記す（0件は「なし」）。承認だけで実装必須判断を補完せず、解決・明示除外・ユーザーの判断委任まで影響範囲を止める。大きな実装は個別着手前に全体目的、主要機能/画面/流れ、対象内外、構成/依存、段階の概要を提示して承認を得る。部分承認はその範囲だけ開始。子へ親仕様版・承認範囲・根拠を渡す。単なる分割、承認内の通常検証・修正は再承認不要。
5. **改訂**：振る舞い/UI/範囲/重要設計を変える場合、影響範囲を止め、説明・仕様・モックを更新して再提示・再承認する。意味不変の誤字等は承認範囲を維持し差分を記録する。影響結果は再検証する。

記録は既存タスク仕様パケット（`docs/harness/tasks/<id>.md` / 既存CLIの `<id>.json`、[雛形](../../assets/task.md)）を正本とし重複仕様を作らない。資料参照/版、提示証拠（会話位置・表示先等）、UI非該当理由、制約を記す。独立承認欄に状態・仕様版・範囲・ユーザー発言根拠、未解決欄に判断回答を記す。承認待ちはplanned/承認pending。readyには提示・承認と実装必須判断の解決/明示除外/委任が必要。新enum/schemaは増やさず既存自由欄等を使う。保存OFFは同内容を会話内で提示・記録しインライン引継ぎする。

ready移行・担当受領・レビューで現仕様版と承認範囲/根拠の一致を確認。不足/不一致は担当から親へ戻し着手しない。改訂時は資料・提示証拠・承認欄を更新し、完了時は最新版の受入条件と提示/承認証拠を確認する。
