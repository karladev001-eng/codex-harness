# 並列実行と統合

担当範囲と依存関係は、分割する前に決めます。共通APIの契約を先に固定し、同じ契約を同時に変更するタスクには依存関係を付けます。小さすぎる分割は、引継ぎと統合の手間が増えるので避けます。

各実装担当には、明示的に選んだコミット済みの基点から、個別のGit worktreeを作ります。基点はパケットにも記録します。先行タスクの変更が必要なタスクは、先行の成果がレビューを通過して取り込まれたコミットを基点にします。最終統合用のworktreeも分離します。

関連する未コミットの変更がある場合、勝手なcommit、stash、reset、削除は行わない。チェックポイントを作るか、現在のcheckoutで直列に進めるかをユーザーに確認し、独立した作業は続けます。非Git環境は直列で実行し、その理由を伝えます。初期リポジトリの構築も、コミット済みの基点ができるまでは直列とし、担当範囲を分けます。

補助CLIは、調整用の `docs/harness/` と `.harness.json` 以外に未コミットの変更があるcheckoutからは、worktreeの作成を拒否します。調整用の文書を保存しただけなら、チェックポイントは不要です。未コミットのパケットは子のworktreeに存在しないので、インラインで渡すか、調整元checkoutへの絶対パスで渡します。プロジェクト設定も子の基点にない可能性があるので、実効設定はプロンプトに含めます。既存の変更を巻き込んでコミットしない。

同時実行の枠は、子の総数で数えます。依存先が完了していないタスクと、同じcheckoutを編集するタスクは、並列で起動しない。読み取り専用のレビューも枠を使います。終了した担当を解放して、次の準備ができたタスクを開始します。

worktreeやブランチに既存のものと衝突する場合は、上書きしない。補助CLIが支援するのは作成だけで、スケジュール、統合、削除は自動化しません。完了時にも、取り込まれていない変更は残し、ユーザーの承認なしに作業領域を削除しない。
