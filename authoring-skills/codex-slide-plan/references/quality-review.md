# 見た目・ページの要点・全体の流れの審査

制作 → build → 見た目/内容の審査 → 正本の修正 → 新版build・再審査を行う。短い資料でも三つの審査を省略しない。審査はCodexの制作工程で行い、ブラウザにAI判定・外部APIを追加しない。利用可能なら制作担当とは別のレビュー担当を使い、担当が使えない場合は制約と自己審査を区別する。

## 全ページの見た目（visual）

利用可能で許可された表示環境で生成HTMLを開き、フォントと画像の読込を待つ。全ページ・全案をレビュー内/単独/一覧/拡大で確認する。狭幅360px・通常768px・広幅1440px相当とレビュー埋込幅の変化、開閉後・リサイズ・拡大解除、4:3/16:9を対象にする。

重なり、はみ出し、欠け、揃え、ラベル、行間、コントラスト、本文とフッターの間隔を確認する。枠内に収まるだけで確認済みにせず、文字の読みやすさと視線の順番も見る。基準キャンバスへ逆変換した座標・改行と画像を比較し、丸め/アンチエイリアスと配置の変化を区別する。境界外・文字あふれ・フッター交差の座標検出は補助。背景や図形内ラベルなど意図した重なりは理由付きで記録し、すべてをエラーにしない。

実際の生成HTMLのスクリーンショットと、必要な座標記録を保存する。テキストだけのDOM adapterや構造テストは実表示の証拠にしない。表示できなければ `pending` と未検証理由を残す。拒否された表示経路をlocalhost・headless・setContent等で迂回しない。旧版の画像、モック、開く処理の成功を修正後の確認証拠に流用しない。

## 各ページの要点（page）

各 `message` を一文で言い直し、見出しと主役の図・数値・言葉が同じ要点を示すか確認する。同じ要点を支える比較値/条件と、別の結論/問いを区別する。別の主張は分割し、図表の長文による言い直しは説明/原稿へ移す。視覚化に適した内容で図表を選んだか、説明文は最小限か、必要な単位・条件・仮値表示を残したかを見る。

図表を元データ・集計コード・原稿と照合する。値だけでなく、軸の起点、尺度、比較条件、標本/母数、欠測、期間、短縮率の分母を確認する。読めても要点が不明な図や、棒長と値が対応しない図は修正する。結果と実運用への推論を分け、仮想値を測定実績にしない。

## 全体の流れ（flow）

原稿をページ順に通読し、聞き手の前提・初出語、前提→結果→限界→次の行動の論理、つなぎ、図表と原稿の一致、持ち時間を確認する。この順番を固定ページ構成として強制せず、目的に合う筋になっているか判断する。枚数追加・分割時は原稿と時間配分も見直す。実際の聞き手評価やリハーサルは別の確認で、通読だけで保証しない。

## 記録と再審査

正確なJSON契約・CLIは [schema.md](schema.md) の `reviews` を使う。記録は `visual`/`page`/`flow` を分け、全ページと全案をカバーする。deck/revision/variant、内容+デザインの `contentHash`、描画CSS/JSを含む `rendererHash`、データ・素材原本のbytesに対応する `artifactHash` を一致させる。確認者・日時・自己/独立・実表示/意味/構造・環境・証拠path/hash、チェックの理由、未確認事項を残す。証拠は `evidence/` 下へ保存し `files` に明示する。指摘はslide/element/段落ID、重要度、問題、理由、修正案、解消状態を持たせる。

- `pending`: 審査待ち/未検証。確認できない範囲と理由を `unchecked` に残す。
- `changes`: 要修正。特に重大指摘を残した成果物は完成扱いしない。
- `verified`: 実施した対象・方法で確認済み。visualには実表示と証拠が必要、page/flowには意味内容の実審査が必要。

修正後は同じ新版のHTML・根拠・原稿を対象に再審査する。指摘の解消理由と新版の証拠を残し、旧版の判定は履歴に保つ。内容・配置・描画runtimeが変わった記録は失効/審査待ちとして扱う。証拠追加だけで内容hashを変えず、審査記録は内容hashから除外する。確認済みの内容審査があっても、未検証の見た目をまとめて合格にしない。
