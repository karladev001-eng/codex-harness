# 並列実行と統合

担当範囲と依存関係を分割前に決める。共通APIの契約を先に固定し、同じ契約を同時に変更するタスクは依存関係を付ける。小さすぎる分割は引継ぎと統合の消費が増えるため避ける。

各実装担当には、明示的に選んだコミット済み基点から個別Git worktreeを作る。基点はパケットにも記録する。先行タスクの変更が必要なタスクは、先行成果がレビューを通過し、取り込まれたコミットを基点にする。最終統合用worktreeも分離する。

関連する未コミット変更がある場合、勝手なcommit、stash、reset、削除を行わない。チェックポイントを作るか現在のcheckoutで直列に進めるかユーザーへ確認し、独立した作業は継続する。非Git環境は直列実行とし、その理由を伝える。初期リポジトリ構築もコミット済み基点ができるまでは直列で担当範囲を分ける。

補助CLIは調整用の `docs/harness/` と `.harness.json` 以外に未コミット変更があるcheckoutからのworktree作成を拒否する。調整用文書を保存しただけならチェックポイントは不要。未コミットのパケットは子worktreeに存在しないため、インラインまたは調整元checkoutへの絶対パスで渡す。プロジェクト設定も子の基点にない可能性があるため、実効設定をプロンプトに含める。既存の変更を巻き込んでコミットしない。

同時実行枠は子の総数で数える。依存先が完了していないタスク、同じcheckoutを編集するタスクは並列起動しない。読み取り専用レビューも枠を使う。終了した担当を解放して次の準備済みタスクを開始する。

worktree/ブランチの既存衝突は上書きしない。補助CLIは作成だけを支援し、スケジュール・統合・削除を自動化しない。完了時も未取り込み変更を残し、ユーザー承認なしに作業領域を削除しない。
