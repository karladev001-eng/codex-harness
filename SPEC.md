## Goal and scope

Preserve quality and consistency while reducing Codex subscription usage per completed task. Main agent owns specifications, decisions and coordination; all product implementation is delegated. Independent tasks run concurrently, with three child slots by default (bounded by host capability). Deterministic tasks use lighter models; reviews use stronger models. No claim of savings until measured.

V1 includes task handoffs, model routing, isolated parallel implementation, independent review, persistent decisions, feature flags, portable setup/doctor/uninstall, measurement records, and an instruction-based loop for UI/document feedback. Designer automation, automatic compaction and transcript deletion remain outside the implemented scope. Knowledge storage/sync/retrieval and optional capture/search integrations are subsequent implemented extensions described in the current reading guide. Required preimplementation visual mockups are instruction-based preparation and are not excluded by the Designer automation boundary. No daemon, API key, hosted service, or automatic publishing.

## Distribution and interfaces

Repository contains TypeScript implementation in `src/`, Markdown/plugin source in `plugins/codex-harness/`, six independent `authoring-skills/` (four Markdown-only tools, `codex-html-plan`, and `codex-slide-plan`), Node tests and Japanese README. The two HTML skills carry Node.js 22+ pack runtimes; codex-html-plan also includes its Apache-2.0 license. Build emits standalone `dist/skill/runtime.js` and the complete `dist/plugins/codex-harness/` plugin. Node.js 22+ and npm are required; Git is used for worktrees. No production dependencies or consumer-side TypeScript compilation. Python helpers are used to inspect PPTX masters and build fixtures, not required to run the packed HTML tools. Build precompiled local npm tarballs and copy them to the receiving PC; run `npx --yes --package ./archive.tgz codex-harness ...`. Existing 0.4.2 tarballs contain the prior five skills; the checkout's new sixth skill is prepared for a future distribution. `private: true` prevents npm registry publication. Private GitHub Release assets and authenticated `gh release download` were an earlier distribution proposal, not a prerequisite or a claim that the current archive is published.

CLI: `codex-harness status|doctor|install|uninstall|task|worktree|measure|preferences|authoring` (development: `node dist/skill/runtime.js` after building). Subcommands and options documented in the [CLI reference](plugins/codex-harness/skills/harness/references/commands.md) and [purpose-specific guides](docs/README.md). Every filesystem mutation is explicit. `status --project PATH` resolves defaults, personal settings and project overrides and emits JSON. Configuration file names: personal `$CODEX_HOME/harness/settings.json` (default `~/.codex/harness/settings.json`); project `.harness.json`. Host-local runtime data goes under `$CODEX_HOME/harness/projects/<hash-of-canonical-project-path>/`.

Install uses a copied standalone skill under `~/.agents/skills/codex-harness`; `--skills-dir` explicitly overrides its parent directory. Provide `--home PATH` isolated user-home override for tests and reproducible installations; resolve CODEX_HOME when no override. This standalone-skill route is the zero-marketplace setup; retain valid plugin packaging for Codex plugin distribution, and clearly document the distinction. Do not require or edit marketplace configuration for standalone setup.

Install adds a uniquely delimited bootstrap to `$CODEX_HOME/AGENTS.md`, preserving existing content and settings, and installs the skill with its required runtime/assets together. The bootstrap reaches coding, UI/document creation or revision feedback, and Web search/research. Preflight ownership/collisions, back up managed previous version, preserve user settings, refuse to overwrite user-modified managed files on update/uninstall. Repeated installation is idempotent. Uninstall removes owned registrations/instructions only and retains project documentation, personal settings, and host-local creative preferences. Read unmodified legacy schema-1 installations without executing Python; emit schema-2 ownership manifests. Preserve exact unrelated instruction bytes and settings. Managed block points at permanent installed runtime.js, not npx cache. Restore JavaScript releases by rerunning install from the desired tarball. To restore Python releases, uninstall using the JavaScript CLI first, then follow the historical release instructions. No global model or Codex concurrency configuration changes.

Authoring skills install independently with `authoring install|uninstall --project PATH`, defaulting to `.agents/skills`. Optional repeatable `--skill NAME` selects a subset and `--skills-dir PARENT` supports explicit personal destinations. A separate ownership manifest governs updates and removal. Preflight all selected targets before mutation, refuse edited/unowned collisions, roll back failures, and never activate orchestration or edit AGENTS.md implicitly.

## Configuration

JSON object with `schema_version: 1`, booleans `enabled`, `delegation`, `review`, `persistence`, `measurement`, `improvement_loop` (default true), `model_selection` enum auto/fixed (default auto), `max_agents: 3`, and `models` mappings. The child defaults are `deterministic` = gpt-6-luna/low, `standard` = gpt-6.1-sol/medium, `complex` = gpt-6.1-sol/high, `review` = gpt-6.1-sol/high. Each contains `model` and `reasoning_effort`. Optional `preferences` mapping defaults to `{repository:"", branch:"main", project_key:""}`. A configured destination requires GitHub.com owner/repo, an existing branch and a shared project key of 1–64 letters/digits/underscores/hyphens. Empty repository and project_key retain the local backend. Unknown keys, wrong types, invalid concurrency and unsupported schema fail clearly. Merge nested mappings defaults < personal < project. These settings do not switch the main host model: gpt-6-astra is requested for the main coordinator, but a differing host value must be reported. Model and effort availability must be verified by the executing host; unavailable selections are surfaced, not silently replaced. Honor explicit user overrides.

All feature flags independent. `enabled=false` OR all five feature flags false means inactive: status check only, no agent launches, project records, logs or measurement. With delegation off main can implement normally; review remains independent if enabled. With persistence off use inline handoffs and no persistent task documents. Runtime metadata required for explicitly requested worktrees remains local. Re-evaluate flags at task boundaries. Invalid configuration must not silently activate features. For legacy configurations, if all four old flags resolve false and neither override layer specifies improvement_loop, resolve the new flag false to preserve inactivity; explicit true takes precedence.

For creative work, inactive or improvement_loop=false means no automatic preference reading, recording, application or candidate trials. Retain saved memory and continue ordinary within-request corrections. Explicit memory inspection/correction/forgetting requests are separate operations even with the loop off, but persistent memory reads/writes still require persistence=true. Task persistence and the improvement loop are independent. With persistence off, do not read historical preference files and keep feedback only in the present conversation. With measurement off, explicit preference evidence may still be recorded when persistence is on, but no usage counts, aggregates, or measurement logs are stored. Missing evaluation is `unknown` / `null`, never inferred improvement.

## Orchestration protocol

Bootstrap applies automatically to coding requests across projects, but excludes child recursion: a delegated worker performs its bounded assignment without invoking coordinator workflow. Existing higher-priority project/environment constraints prevail. This is instruction-based orchestration, not a scheduler enforcement guarantee.

The bootstrap also reaches UI/document creation, revision, and related feedback. Pure creative tasks use the creative loop without requiring code delegation, Git worktrees, or code integration. Work that changes code retains implementation review under the existing `review` flag. Current user instructions, permissions, and safety constraints always outrank stored preferences. Exploration requests permit new styles instead of forcing a prior one.

For active Web research or answers drawing on Web sources, cite major supporting pages with descriptive Markdown links near their claims, preferring primary sources. Use actual evidence-page URLs, never search result pages, internal reference IDs, or invented URLs. Papers include verified title, authors (first author et al. if numerous), year, and a DOI URL or direct publisher/arXiv paper link; unknown metadata stays unknown. Disclose limited reading scope such as abstract-only when it affects the judgment, distinguish inference, and never claim to have read unavailable text. Before completion verify links, claim support, bibliographic facts and reading scope. Citations belong in the answer; update an existing research packet only when needed, honoring persistence=false without creating records solely for this rule. Pure Web search/research applies this rule and returns to ordinary answering without code delegation, Git worktrees or integration. This neither mandates search nor changes host citation UI; inactive behavior and higher-priority/user instructions remain unchanged.

For active implementation requests, including new features and fixes, main creates and presents an explanation and specification to the user before product implementation or an implementer start instruction. UI creation or revision also requires a visual mockup; UI/document creation or revision without code still receives an explanation and specification before production work. Small changes may use a short specification but are not blanket-exempt. Apply this preparation even with delegation/review/improvement_loop off while active; inactive adds no such workflow. Pure research or specification-only requests do not acquire implementation, code delegation or Git steps.

The specification includes purpose, scope/non-goals, user-visible behavior, necessary inputs/outputs and error behavior (or reasons for inapplicability), numbered acceptance criteria, constraints and open questions. Reuse existing specifications/mockups only after checking fit to the current request. Visual mockups use images, wireframes, renderable HTML or equivalent viewable artifacts covering major screens, interactions and necessary states, linked to the specification revision; prose alone is insufficient. Research, specification and mockup preparation may precede this gate, but production incorporation or real feature implementation may not. If required artifacts cannot be presented or a user decision is essential to resolve an open question, stop implementation start and report the limitation. After required presentation, explicit user approval of the presented specification revision and scope is required before product implementation, implementer start instructions or production incorporation, even with zero open questions. Silence, elapsed time, untouched default selections, answers to questions alone, and a generic implementation request before presentation are not approval. Record answers and implementation approval separately, including both when the same utterance explicitly contains both. Do not repeat approval already explicit for the same presented revision and scope. Honor higher-priority and current user instructions and permission constraints.

For large implementations, present and obtain approval for an overview of overall purpose, major features/screens and flows, scope/non-goals, architecture/dependencies and stages before individual implementation tasks start. Keep open questions separate from settled specification and approval: state none when absent; otherwise include impact, options/proposals, required decisions and owners. Approval alone does not resolve essential implementation decisions: stop the affected scope until resolved or explicitly excluded/delegated by the user. Partial approval enables only its scope. Child tasks inherit the parent specification revision, approved scope and evidence; splitting tasks or ordinary validation/fixes within approved scope does not require repeated approval.

With persistence on, keep the existing task specification packet canonical (docs/harness/tasks/<id>.md or the existing CLI-generated <id>.json, reusing either without duplication), recording explanation/spec/mock references and revisions, presentation evidence, reasons for UI inapplicability and remaining constraints, plus a separate approval record with status, target specification revision/scope and user utterance evidence. While awaiting approval keep the task planned with approval pending; ready requires presentation, approval and resolution or explicit exclusion/delegation of essential decisions for the applicable scope. Do not create a duplicate standalone specification. With persistence off, perform and record the same preparation/presentation in conversation and hand it off inline. Confirm current revision, presentation completion and approval scope/evidence at ready transition, implementer receipt and review; implementers return missing/mismatched preparation to main without starting. For specification changes affecting behavior, UI, scope or important design decisions, stop the affected scope, update and re-present explanation/spec/mockups and obtain reapproval before proceeding; update evidence and revalidate affected results. Typographical or other meaning-preserving edits retain approved scope with a recorded diff. Completion confirms latest acceptance criteria and presentation/approval evidence. Use existing free-text record fields where needed; add no state enum or CLI schema. This durable rule is canonical in the existing [SKILL entrypoint](plugins/codex-harness/skills/harness/SKILL.md#実装前の説明仕様視覚モック), uses the existing task template/reviewer and adds no runtime execution blocker, configuration key or duplicate HARNESS.md/AGENTS.md.

Main creates one task packet per independent unit: ID, goal, non-goals, numbered acceptance criteria, scope/owned paths, dependencies, specification revision, code base revision, constraints, source references and open questions. It records dependency graph before dispatch, rejects cycles/missing dependencies, and launches ready tasks only, confirming preimplementation presentation and approval for applicable implementation/production tasks. Research, specification and mockup preparation are not blocked by this implementation start condition. Explicitly spawn with no parent history using supported host mechanism; if unavailable report incompatibility. Shared spec and necessary files are available by reference. Children never recursively spawn.

Choose each child's model first from task nature, then choose reasoning effort independently for the quality required. Luna suits a clear answer with easy verification, simple implementation following an established pattern, or bounded research; objectively defined work remains Luna-eligible across multiple files. Sol suits open-ended design or architecture, important review, and risky problems such as authentication, migration or concurrency. The default keys are starting points, not fixed effort levels for roles. Use low for straightforward objectively checkable work, medium for ordinary careful work, high for rigorous work and review, and xhigh/max only for justified exceptional quality. Respect the efforts supported by the host for the chosen model. Record the chosen model, effort and concise reason in the task packet. Ambiguous requirements return to main. Research delegation is optional only when exploration is substantial. Implementer returns result, changed paths, checks with evidence, unresolved issues and commit ID. No raw logs in main.

Each parallel implementation has a Git worktree at an explicitly selected committed base. Never reset, stash or delete user changes. If relevant work is uncommitted, ask to choose checkpointing or use serial work in current checkout; do not drop it. Worktree helper validates task IDs, refuses branch/path collisions and checks repository/base. Non-Git projects use serial execution and explain why. Initial repository bootstrap can use distinct owned paths serially until a committed base exists.

Each implementation gets a separate reviewer if enabled. Reviewer uses packet + actual diff + surrounding code + validation evidence, not implementation transcript. Output verdict PASS/NEEDS_WORK/BLOCKED, criterion coverage, findings with severity/location/evidence, checks and limitations. Review-only agents do not edit product code. Fix and review at most two rounds; unresolved issues go to main, not auto-pass. After task-level review, delegated integrator combines approved commits on integration worktree in dependency order, runs integration checks, and obtains final cross-task review before completion. Main resolves specification decisions; integration code edits remain delegated. Never auto-merge/push external branches.

Reusable role procedures cover paper discovery, primary-source verification, Web UI evaluation, and independent code review. Load only the applicable procedure. Main assigns research partitions and stop criteria, deduplicates candidate IDs, and keeps discovered and verified counts separate. Web UI evaluation is optional when an acceptance condition and browser access exist; it is not an automatic v1 stage. A reviewer forms an independent risk checklist before reading implementation test claims and evaluates actual diffs, including applicable data collision and failure recovery cases.

States: planned -> ready -> implementing -> reviewing -> done; needs_work returns to implementing; blocked requires reason; ready requires current preimplementation presentation/approval evidence and essential decision resolution or explicit exclusion/delegation for applicable implementation/production tasks only; approval waiting remains planned with approval pending; integration and completion validate current spec revision and code revision. Completion requires acceptance checks and review PASS when review enabled. Spec changes invalidate affected results and dependent integration; completed tasks not reread wholesale.

## Host model selection

Resolve settings and model provenance in the same operation. Status returns config.models as configured baselines, model_selection.mode, resolution (host-launch for auto, configured for fixed), catalog_checked=false and pinned_roles/pins with personal/project source paths. Status never chooses a host successor or claims configured values are live dynamic selections; it is read-only and offline.

At task start and each child launch, the parent checks the actual launch tool's models, descriptions and supported efforts. Cross-check any optional CLI catalog with that launch surface. In auto, only choose a same-role, same-family successor when the host explicitly identifies an upgrade/latest relationship or equivalent evidence. Public Web lists and name guesses alone are insufficient. Do not automatically change lightweight work to a top-cost model family. Fixed uses existing configured mappings. Explicit personal/project models.<role>.model pins that role in auto (project overrides personal); effort-only overrides do not pin the model. Current user overrides take precedence. Without a catalog or unambiguous successor evidence, use the configured baseline and report the limitation. Unsupported explicit model/effort values are reported, not silently substituted.

Record catalog/source and supported efforts, evidence/reason and actual model+effort in the packet (inline with persistence off). Catalog listing does not guarantee entitlement or launch success; do not record failed launches as successful. Never switch running children. Apply the same procedure on other PCs. This instruction-based selection adds no network/authentication/API client or background monitor to the runtime and cannot guarantee updating immediately on a model release. Future successor execution remains unverified until actually launched.

## Persistence and measurement

Project `docs/harness/` stores project map, tasks, and ADRs; create only when needed, not for every folder. Task records hold compact specification, progress, completion and evidence references. ADRs record consequential choices with rationale, not all conversation. Runtime logs and measurements remain host-local. Session restart accepts a task ID and rereads current packet + relevant decisions, not whole archive. Cross-PC handoff requires committing/syncing code and documents; active agents/worktrees are not migrated.

Creative preferences default to `status.local_root/creative/preferences.md`, outside installed ownership. Explicit `preferences.repository/branch/project_key` makes `improvement/projects/<project-key>/preferences.md` in a private GitHub.com repository canonical. Runtime read/write/sync/migrate uses existing gh authentication with explicit hostname and stdin JSON; no credentials or transport response/error bodies are persisted. Status reports destination metadata without memory reads/network/writes. Configuring GitHub alone never uploads the old local file. If absent, start empty without an initial questionnaire or permission gate. A user may explicitly transfer a minimal guideline between projects; no automatic cross-project sharing. The parent validates evidence, target and final decisions, and gives creative workers only guidelines needed for their assignment. The default record-keeper owns saving/updating/resynchronizing the file under the bounded contract below. The four distinct record types are observations, candidate hypotheses, applicable guidelines, and trial outcomes. Records carry stable item/evidence IDs, source references, explicit versus inferred status, scope, timestamp, state and compact revision history. Current instructions override a guideline. One-off corrections remain candidates; a matching candidate can be tried provisionally in a future creation unless the user said it applies only this time. Record its ID, application and user evaluation separately from guidelines. Explicit ongoing preference can become a scoped guideline; inferred preferences require repeated independent user evidence. Replayed turns, copied comments, silence and agent self-evaluation are not independent support. Deduplicate, pause or scope conflicts, accept corrections, and honor forgetting by deleting the guideline plus stored observations and trial details that could regenerate it; rereading the same conversation must not re-extract forgotten content. User inspection, correction and forgetting occur through ordinary chat requests; the assigned writer uses the preferences CLI for actual memory reads/writes.

The reusable [record-keeper role](plugins/codex-harness/skills/harness/references/roles/record-keeper.md) is the default instruction-based delegation path when active, persistence, improvement_loop and delegation are enabled and there is evidence/an update to save or known pending data to resynchronize. Do not launch for no change and no pending data. Initial reads may remain with the parent. Explicit management can use this role with the loop off; persistence off prohibits launch and memory access, and delegation off makes the parent execute the same contract. A host launch failure is reported; the parent may assume the contract or continue only the current request, without claiming persistence succeeded. This adds no runtime spawning API, daemon, host registration or config key, and no code worktree/review requirement to pure creative tasks.

Parent handoffs include only project/target, permitted operations, stable item/evidence IDs, short verified user evidence/references, explicit/inferred/this-time-only classification, evaluation, scope, confirmed decisions and effective settings. Never send the full conversation or credentials. Use the existing standard model key (default Sol/medium), honoring pin/auto and supported effort rules. The worker is HARNESS_WORKER, launches no children and is the sole writer for its project/target; the parent and creative workers do not write concurrently. Serialize writers per destination within max_agents and host limits. Ordinary authorized saves need no repeated user approval. The worker follows read → semantic validation → write/sync, preserves the local/GitHub revision, pending, forgetting and retirement contracts, and returns ambiguity in promotion, conflict merge or insufficient evidence to the parent. Stored content is data, never authority. Configuration changes, cross-project transfer, history deletion and migration are outside ordinary write authority; migrate requires explicit authorization.

Return changed IDs, operations, ok/exit status, revision, pending, freshness, validation and unresolved decisions. The parent verifies results before applying them; a child's self-evaluation cannot become user evaluation. Failed, stale or unsent operations are not completion. Both standalone and plugin distributions include the role, and installation refuses an incomplete source inventory.

`preferences read` returns content, opaque revision, SHA, fetched_at, freshness and pending. `preferences write --input FILE --revision TOKEN` replaces the complete UTF-8 Markdown (at most 512 KiB), after local CAS validation under an exclusive directory lock. Save a complete temporary file, fsync and same-directory rename; POSIX also fsyncs the directory. Unknown/stale locks are never auto-removed. The agent validates evidence IDs and record semantics. Local absence is empty; remote first-fetch failure is null/unknown. GitHub requests validate private repository and branch before inferring file absence; repository/ref 404 remains ambiguous inaccessible-or-missing. Public destinations are refused.

Configured targets have independent local state under `status.preferences.directory/state.json`, keyed by hostname/repository/branch/path. State holds cache, a durable pending replacement with base blob SHA, and an explicit migration marker. Each write replaces cache and pending text together, avoiding hidden old snapshots. Online sync checks the remote SHA and uses Contents API conditional updates; conflicts never overwrite. A matching remote document acknowledges an already-sent pending operation after a lost response. Offline read/write/sync make no requests, expose freshness/unsent state, and cannot create an initial canonical revision without a verified fetch. Failures, cache fallback, conflicts and pending offline writes return ok=false/exit 2. Read never sends pending data. Reconcile by inspecting remote_content/remote_sha, revising by evidence IDs, then writing with the current local revision and explicit `--base-sha OBSERVED_SHA` (or missing for confirmed absence); another concurrent edit still conflicts.

`preferences migrate` is explicit, online, preserves the old local source, and refuses differing existing remote content. The target-specific migration marker is persisted with the draft. A content-free project-local `creative/legacy-retired.json` then permanently retires the source under the local backend lock, before any remote transmission. Sync repairs missing retirement metadata before sending and stops if its durable save fails. Failed saves report reloaded durable state (empty if no state file), never in-memory pending. Pending=false after a failed draft save means migration must be retried. The local backend refuses read/write/sync of a retired source even after destination configuration removal; restore GitHub configuration to use the current canonical record. A different destination also cannot remigrate a retired source; explicitly transfer current canonical content instead. Configured reads never fall back to the legacy original. After migration, runtime prevents configuration removal or target changes from reviving the legacy source; agents must not scan Git history to reconstruct it. Forgetting/correction removes reconstructable records from current content/cache/pending and conditionally updates canonical content; offline/conflicting remote deletion remains incomplete and must be reported. The retained legacy source and user-provided input files require separate correction/removal when requested. No Git-history or other-PC stale-copy purge is guaranteed. Automatic creative application requires a fresh, successful remote read with no pending data; stale/cached/pending data is inspection-only so offline copies cannot automatically revive forgotten preferences.

Persistence OFF prevents all memory reads/writes/network, including explicit management. Loop OFF stops the automatic workflow while allowing explicit management with persistence ON; measurement is independent. Corruption, dangling references or save failure stop affected memory use/update but do not stop creative work. Installer update/uninstall does not touch memory. Long-term quality improvement is unverified. This one-file preference stage supersedes ADR 0002's local-only preference boundary. Page capture, fetch-based knowledge synchronization, character search and extensions were future work at that stage and are now separate implemented Knowledge features. Preference records remain separate from saved source material; the later contracts are in ADR 0004–0006.

Measurement records baseline/harness condition, task/run IDs, start/end, elapsed time, model roles, corrections, completion/defects, optional account usage before/after and reset-window identifiers. Missing values remain null. Account-wide deltas are not exact task costs; overlapping runs or reset windows are invalid for comparison. No token-to-quota conversion. Benchmark 3 task classes x 3 repetitions x 2 conditions manually/explicitly triggered; no automatic expensive benchmark. Track lower median quota use with no quality regression; otherwise report unconfirmed.

## Acceptance and tests

Automated tests use temporary home directories and disposable Git repositories only. Cover layered config and all-off no-write behavior; malformed flags/schema; safe idempotent install/update/uninstall including unrelated AGENTS content, custom CODEX_HOME, paths with spaces, collisions and user edits; task IDs and document creation; isolated worktrees, dirty files retained, invalid refs/collisions; measurements unknown/reset/overlap. Validate plugin manifest and skills using supplied validators.

Manual live acceptance: host honors model/no-history spawning; multiple isolated tasks overlap; review catches seeded defect; integration catches cross-task mismatch; restart/cross-PC packet resume; feature flags respected. Report these separately from unit tests and do not claim live validation from document checks. macOS locally tested; Windows/Linux portability designed, unverified until run there.
