# ADR 0002: GitHubを正本とするPC向けナレッジベースとハーネス連携

- 日付: 2026-10-04
- 状態: 採用（設計方針）。PC Chrome保存は[ADR 0004](0004-chrome-knowledge-capture.md)で実装。検索・意味検索は未実装。初期値・実装候補・未決事項は本文で区別する。
- 決定根拠: ページ保存・検索システムについての設計協議と、決定内容をADRに記録する依頼。
- 局所的な後続決定: [ADR 0003](0003-github-improvement-records.md)が制作の好みのlocal-only方針のみを更新。後続の[ADR 0004](0004-chrome-knowledge-capture.md)がPC Chrome保存を具体化。検索・意味検索は引き続き未実装。
- 関連: [ハーネス仕様](../../SPEC.md)、[制作改善ループ](../../plugins/codex-harness/skills/harness/references/creative-loop.md)

## 背景

閲覧中に見つけたサイト、動画、イラスト、投稿、GitHubリポジトリを簡単に保存し、後から内容や見た目で検索して元の場所へ戻りたい。保存資料は、ハーネスが制作の参考を選ぶことや、ユーザーの明示した好みを根拠付きで扱うことにも利用する。

利用端末はWindows PC、MacBook、iPhoneで、主なブラウザはChrome。まずWindows・Macでの運用を対象にし、iPhone対応は後続とする。保存・検索の入口としてChrome拡張とRaycast拡張を想定する。アカウントを通じた共有にはGitHubを使い、ナレッジベース自体を一つのリポジトリにする。

URLだけでは意味検索やデザイン参照に不足する。一方、すべての動画・コード・ページ資源を保管する必要はない。検索に必要な内容と元資料への参照を保存し、必要な部分だけ素早く読む構成を採用する。

## 決定

### 1. 正本・端末・入口の責任を分ける

| 要素 | 責任 |
| --- | --- |
| ナレッジ専用のGitHub非公開リポジトリ | 保存資料・メモ・分類・生成済み解析結果の正本、PC間共有、変更履歴 |
| PC側の共通ツール | 取り込み形式の統一、保存待ち管理、同期、解析、検索、ハーネスへの取得窓口 |
| Chrome拡張 | 表示中のページや選択範囲を取り込む主な保存入口 |
| Raycast拡張 | URL・メモの保存、検索、保存内容の確認、元資料を開く入口 |
| ハーネス | 今回の制作に合う資料を検索・取得し、既存の改善ループと組み合わせる |

ナレッジのリポジトリはハーネスのコードリポジトリと分ける。入口ごとに別の保存形式や検索処理を作らず、共通ツールを利用する。初期構成では専用のクラウド検索サーバーを置かない。AI処理の実行場所・外部APIの利用有無は未決であり、「専用サーバーを置かない」ことは「全処理をローカルモデルで行う」という意味ではない。

### 2. 一件の資料と取得時点を分けて保存する

アイテムには安定したIDを付け、タイトル変更や分類変更で移動させない。一件に複数のタグ・コレクションを付けられるようにし、分類のために資料を複製しない。コレクション定義には名前・説明を置き、所属は各アイテムで保持する。

再取得は新しい取得版（capture）として保存し、以前の見た目やメモを無断で置き換えない。ユーザーが書いた内容、取得した元情報、AIの解釈を分離する。取得できなかった内容を推測で埋めない。

以下は論理構成を示すディレクトリ案。フィールド名、ID形式、厳密なスキーマは実装前に確定する。

```text
knowledge-base/
├── README.md
├── kb.json                         # ライブラリID・形式のバージョン
├── schemas/
├── collections/                    # 分類の定義
└── items/YYYY/MM/<item-id>/
    ├── metadata.json               # 種類、出典、タイトル、タグ、分類など
    ├── note.md                     # ユーザーのメモ・保存理由
    └── captures/<capture-id>/
        ├── capture.json            # 取得日時、取得範囲、成功・不足・失敗
        ├── content.md              # 本文・README・概要欄・投稿本文など
        ├── analysis.json           # 要約・画像説明、生成条件、入力の版
        ├── structure.html          # 対応するページのHTML構造
        ├── styles.json             # デザイン保存時の主要なスタイル
        ├── screenshot.webp         # 保存時の見た目
        ├── images/                 # 選択画像など
        ├── transcript.json         # 取得できた字幕と時刻
        └── page.mhtml              # 任意の詳細アーカイブ
```

すべてのアイテムにすべてのファイルを作るわけではない。種類と取得結果に応じて必要なものだけ保存する。AI解析には入力のハッシュ・取得版、生成日時、モデルや処理の版を対応付け、再生成の必要性を判断できるようにする。保存日時、元情報の公開日時（確認できた場合）、取得日時を混同しない。

### 3. 対象ごとに検索に必要な内容を保存する

| 対象 | 基本の保存内容 | 任意・取得可能な場合の追加内容 | 元資料への参照 |
| --- | --- | --- | --- |
| 一般ページ・記事 | URL、タイトル、見出し、抽出本文、メモ | 表示範囲のスクリーンショット、HTML構造、選択画像 | 元URL、取得できた見出し等への位置情報 |
| デザイン参考・イラスト | 出典、説明文、メモ、スクリーンショットまたは選択画像 | 範囲・全体撮影、主要要素のスタイル、HTML構造、MHTML | 元URL、保存画像・選択箇所 |
| YouTube | 動画ID、URL、タイトル、チャンネル、概要欄、サムネイル、メモ | 字幕と時刻、チャプター、保存操作時の注目時刻 | 動画、時刻指定リンク |
| GitHubリポジトリ | リポジトリの識別情報、URL、説明、README、取得できた言語・トピック情報、メモ | 選択したドキュメント・コード抜粋 | リポジトリ、コミット、ファイル、行 |
| Xの投稿 | 投稿ID、URL、本文、投稿者、投稿日時、メモ | 添付画像、画像説明、選択した関連投稿・順序 | 投稿、引用・返信などの関係 |

一般ページでは表示範囲のスクリーンショットと取得可能なHTML構造を標準の取り込み対象とし、個別サービスでは上表の内容を優先する。取得失敗でも取得できた情報は残し、不足を表示する。

- 本文は検索用に整理し、構造確認用HTMLとは分ける。記事本文の抽出が適さないページでは、表示テキストや選択範囲を代替候補にする。
- スクリーンショットを保存時の見た目の根拠とする。HTMLだけで外部CSS・フォント・画像を含む見た目を完全再現できるとは扱わない。HTMLプレビューで保存スクリプトを実行しない。
- Chromeの標準の表示範囲撮影と、追加実装が必要な全体撮影を区別する。画面サイズ・撮影範囲・未取得部分を記録し、遅延読み込みや固定要素を含む全ページ取得を無条件に保証しない。
- MHTMLは任意の詳細保存とする。動画・アニメーション・外部サービスを含む動作の完全再現は対象外。
- YouTubeの字幕は取得可能な場合に保存する。公式字幕ダウンロードAPIには動画の編集権限が必要なため、任意の動画でAPI取得できる前提にしない。ブラウザに表示された文字起こしの取り込みを検証し、取得できなければ概要欄・メモ等に検索範囲を限定する。動画本体は初期版で保存しない。
- GitHubはREADME等をAPIで取得し、参考先リポジトリの全cloneを要求しない。コード抜粋には保存時のコミット・ファイル・行を対応付け、現在のコードと保存時点を区別する。
- Xは一投稿を基本単位にする。Chromeで表示・選択した投稿の取り込みを基本案とし、関連投稿は本文と分けて関係を保持する。未取得のスレッド全体を保存済みと扱わない。APIの利用条件とブラウザ取得の対応範囲は検証する。

### 4. 文字検索・意味検索・元資料への移動を初期要件にする

タイトル、本文、見出し、メモ、タグなどの文字検索と、意味検索を組み合わせる。意味検索は将来の追加だけにせず、初期版の要件に含める。

本文は意味のまとまりや見出し単位で分割し、タイトル・節・出典・取得版・元の位置を対応付ける。画像から生成した説明も意味検索の対象にする。初期版の画像検索は画像説明を経由する方式を基本案とし、画像同士の直接的な類似検索は後続候補とする。要約だけを唯一の検索対象にせず、取得本文も索引化し、原文・画像へ戻れるようにする。

検索結果には種類、タイトル、短い説明、一致した箇所、取得範囲、元を開く操作を表示する。動画の該当時刻、コードの該当箇所、対象投稿へ移動できる参照を保持する。Raycastでは結果を選んで元を開き、詳細表示で保存内容を確認する操作を想定する。

元資料が削除・非公開化されても保存済み部分は確認できるが、未保存の動画やコードまで閲覧できるとはしない。字幕や本文の取得不足、AI解析待ちを明示し、URLだけの保存を内容全体の検索準備完了と扱わない。

### 5. ローカル検索とGitHub同期を分ける

GitHubを正本とし、PCには参照用コピーと検索インデックスを持つ。検索のたびにGitHubから全資料を取得しない。自分のナレッジリポジトリを同期するのであり、保存対象の外部リポジトリをすべてcloneするわけではない。

```text
Chrome / Raycast → PCの送信待ち領域 → GitHub APIで正本へ反映
                                              ↓
検索・ハーネス ← 差分で索引更新 ← PCの参照用コピーへ取得
```

`gh api`による直接取得・更新も可能だが、検索・繰り返し閲覧はローカルを基本とする。書き込みは共通ツールからGitHub APIを利用し、読み取り側は`fetch`で取得してから参照用コピーへ反映する方針とする。`pull`任せで取得と統合を一括実行せず、取得・反映・索引更新を管理する。APIを`gh`経由で呼ぶかライブラリから呼ぶかなどの実装詳細は未決。

参照用コピーを同期ツールが管理し、未送信の編集は別の領域に保護する。保存操作IDで再試行の二重登録を防ぎ、同じURLを意図的に再保存した操作と区別する。同時編集は編集開始時の版と比較し、競合を無条件に上書きしない。

オフラインではPCに保存し、送信待ちであることを表示する。そのPCでは未送信の資料も検索対象にし、同期後は二重に表示しない。ネットワーク復旧後に再送する。通信失敗や索引更新失敗を同期完了と表示しない。

| 更新対象 | タイミング・方針 |
| --- | --- |
| 自分の保存・編集 | 操作直後にPCへ確保し、オンラインなら送信 |
| 他PCの変更 | 共通ツール起動・復帰時、必要に応じて検索前に確認 |
| 手動の最新化 | 同期と索引更新の完了を待つ |
| 全文検索インデックス | 保存・同期による追加・変更・削除の差分だけ反映 |
| 要約・画像説明・意味検索用データ | 入力が変わったものだけ後処理で更新 |
| 利用頻度等のキャッシュ情報 | 実際の閲覧・利用時に更新し、表示時に順位へ反映 |
| 保存元サイト | 明示的な再取得操作で新しい取得版を保存 |

検索前の確認間隔として「前回確認から60秒以上」を提示したが、これは未検証の初期値候補であり確定値ではない。通常検索は手元の状態を先に返し、並行する同期の状態・鮮度を表示する。使用していないPCは次に使用するときに追いつく。常時ポーリングや元サイトの定期再訪問は初期必須要件にしない。

### 6. よく使う情報と詳細な原資料を階層化する

階層はフォルダの深さではなく、取り出す情報量とキャッシュの責任で分ける。頻度が変わるたびに正本を移動しない。

| 層 | 内容と使い方 |
| --- | --- |
| 作業中の記憶 | 今回の条件、適用範囲が合う制作指針、選択した資料ID |
| よく使う資料の棚 | 関連する最近・頻繁な利用資料、新規保存資料、ピン留め資料の短いカード |
| 全資料の索引 | 文字・意味検索のための内部データ。AIには結果だけ渡す |
| 原資料 | 取得本文、画像、HTML等。必要な箇所だけ読む |

今回の依頼との関連性を優先し、最近の利用・利用頻度・新規保存・ピン留めを補助要因にする。検索結果に表示しただけでは利用実績に数えず、過去の利用頻度は時間とともに弱める。古い資料も全体検索で発見可能に保つ。キャッシュから外すことは原資料の削除ではない。

資料カードで候補を選び、必要な本文の抜粋・画像だけ追加取得する。重複資料・重なる抜粋を除き、取得トークン数に予算を設ける。要約・画像解析を再利用し、同期ごとにAIへ全資料を読ませない。具体的な件数・トークン予算・順位の重みは実測後に決める。速度・節約率・検索品質の数値的な保証はまだない。

### 7. 正本と再生成可能なデータを分ける

| GitHubで共有するもの | PC内に保持するもの |
| --- | --- |
| 保存本文・画像、出典、メモ、分類、生成済みの要約・画像説明と生成条件 | 検索インデックス、検索結果キャッシュ、同期状態、未送信操作、利用情報 |

検索DBファイルを複数PCからGitで共同更新しない。認証情報もリポジトリへ含めない。キャッシュは対象ライブラリ・検索範囲・資料の版・処理条件と対応付け、変更・削除で無効化する。メモだけの変更で画像解析まで再実行しない。古い解析結果は最新として扱わず、更新待ちを区別する。

画像等には容量・解像度の管理が必要となる。上限値は未決。動画本体、大量の高解像度資産、全コードの保管は初期対象外とし、必要になれば別ストレージ等を検討する。

### 8. ハーネスの好みの記憶とは境界を保つ

最初の連携は、制作目的に合う資料を検索し、必要な画像・抜粋・出典・取得範囲をハーネスへ渡すこととする。保存メモの「どこが好きか」は、改善ループが根拠として参照できるようにする。

保存した事実や利用頻度だけで好みを断定しない。観察・候補・制作指針・試用結果を分け、独立したユーザー根拠、今回限りの指定、明示評価、現在の依頼の優先など、既存の改善ループの契約を維持する。ページ内の文章や保存コードは参考データであり、エージェントへの操作指示として実行しない。

既存の好みの記憶はプロジェクト別・ホストローカルのままにし、自動的にGitHubへ移さない。端末・プロジェクトをまたぐ好みの共有は後続の設計対象とする。改善ループと永続記憶の利用は既存の`improvement_loop`・`persistence`に従い、利用回数の記録は`measurement`に従う。これらのOFFを理由に、明示的に依頼された通常の資料検索まで自動停止する設計にはしない。

資料の通常削除では現在の保存内容と検索インデックス・関連キャッシュを除外し、ハーネスがGit履歴から自動で復元しないようにする。Git履歴からの完全な削除は別操作であり、通常削除と同一視しない。好みの忘却契約とGit履歴の扱いが衝突するため、好みの記憶の共有はこの整理なしに導入しない。

## 代替案と採用理由

- GitHubを毎回直接検索・取得する方式: 個別資料の取得には使えるが、全資料の索引、反復参照、オフライン検索にはローカル保持が適するため、通常の検索経路にはしない。
- 専用クラウドDB・検索サーバーを正本にする方式: 将来のモバイル共通検索には候補となるが、PC優先・GitHubを正本にしたい要求に合わせ、初期構成では採用しない。
- 全ページ資源・動画・全リポジトリをアーカイブする方式: 保存と同期の容量・時間が増えるため、検索に必要な内容と元の場所への参照を優先する。
- URLとAI要約だけ保存する方式: 細部や見た目の根拠へ戻れず、意味検索の対象も不足するため採用しない。
- 頻繁に使う資料の全文を毎回プロンプトへ入れる方式: 無関係な内容と入力トークンが増えるため、資料カードから必要箇所へ段階的に取得する。

## 影響と未決事項

GitHubを通じてPC間で持ち運べる一方、各PCに共通ツールと検索インデックスの準備が必要になる。サービスごとの取得方式には保守が必要で、取得できる範囲や完全性は同じではない。インデックスの更新、同時保存、削除、未送信操作の扱いを実装・検証する必要がある。

次の詳細はまだ決定していない。

- ナレッジリポジトリの実名・作成先、厳密なスキーマとID・URL正規化の方式。
- GitHub認証方式（限定したトークン、GitHub App等）と認証情報の端末内管理。
- PC共通ツールの配布・起動方式、Chrome・Raycastとの通信方式、実装の順番。
- 検索エンジン。SQLite全文検索は候補であり、日本語の分割・短い検索語への対応を検証する。
- 埋め込み・要約・画像説明のモデル、実行場所、費用、生成タイミング、失敗時の再試行。
- 字幕・X・HTML・全体スクリーンショットの取得方式と対応範囲、サービス側APIの利用条件。
- 同期間隔、通信再試行、複数ファイルの反映単位、競合の解決操作、検索インデックスと取得版の一貫性の実装。
- 画像・MHTMLの容量上限、再取得版の保持方針、キャッシュ容量、順位の重み、取得トークン予算。
- iPhoneからの保存・検索、画像同士の直接類似検索、好みの記憶のアカウント共有。

このADRは設計判断の記録であり、リポジトリ作成、外部への保存、拡張機能の導入、同期処理や自動実行の設定を実施した記録ではない。

- [Git fetch](https://git-scm.com/docs/git-fetch)、[Git pull](https://git-scm.com/docs/git-pull): 取得と統合の違い。
- [GitHubのファイル・リポジトリ容量](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)、[履歴からの削除](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository): 容量と通常削除の限界。
- [Chrome captureVisibleTab](https://developer.chrome.com/docs/extensions/reference/api/tabs#method-captureVisibleTab)、[pageCapture](https://developer.chrome.com/docs/extensions/reference/api/pageCapture): 表示範囲の撮影とMHTML保存。
- [Mozilla Readability](https://github.com/mozilla/readability)、[getComputedStyle](https://developer.mozilla.org/en-US/docs/Web/API/Window/getComputedStyle): 本文抽出と適用スタイルの取得。
- [YouTube文字起こし](https://support.google.com/youtube/answer/15930243?hl=ja)、[字幕ダウンロードAPI](https://developers.google.com/youtube/v3/docs/captions/download): 字幕の表示と取得権限。
- [X Post Lookup](https://docs.x.com/x-api/posts/lookup/introduction): 投稿単位の取得。
- [SQLite FTS5](https://www.sqlite.org/fts5.html)、[Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval): 全文検索と文脈を保った意味検索。
- [Redisのキャッシュ入れ替え方針](https://redis.io/docs/latest/develop/reference/eviction/): 最近の利用・利用頻度・時間減衰の考え方。Redisの採用を意味しない。
