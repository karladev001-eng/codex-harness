# 仕様から実装・レビューへ

1. メインが本実装・実装担当への着手指示より先に、実装内容の説明と仕様を作成してユーザーへ提示します。UIの作成・変更では視覚モックも提示します。目的、対象範囲と対象外、利用者から見た振る舞い・入出力・異常時、番号付き受入条件、制約・未解決事項を含めます。
2. コード修正の開始時は[技術的知見](improvement-loop.md#技術的な修正の再利用)から関連する少数のfreshなlessonを照合します。提示した仕様版・範囲への明示承認を得てから、承認範囲内の独立タスクを履歴を引き継がない実装担当へ割り当てます。
3. 担当ごとのworktreeで実装と必要なテストを行います。
4. 別担当が実際の差分と受入条件をレビューします。
5. 統合担当が承認済み変更をまとめ、結合検証と統合後レビューを行います。
6. 完了条件を満たした時点で、結果と証拠への参照を保存します。修正記録の有無を判断し、根拠のあるlessonだけを記録担当へ渡し、保存成否/pendingを確認します。無変更・根拠なしなら記録担当を起動しません。

[実装前の説明・仕様・視覚モック](../../plugins/codex-harness/skills/harness/references/routing/preimplementation.md#実装前の説明仕様視覚モック)はactive時の標準手順です。小変更は短くできますが省略しません。画像・ワイヤーフレーム・表示可能なHTML等で主要な画面・操作・必要な状態を確認できるモックを提示し、説明文だけで代用しません。既存資料は現在の依頼との適合を確認して再利用できます。必要な資料の提示後、未解決事項がなくても現仕様版・範囲への明示承認まで本実装・着手指示・production組込みを待ちます。調査・仕様・モック作成は進められます。提示不能等の制約は明示します。沈黙、経過時間、未操作の既定選択、質問への回答のみ、提示前の一般的な実装依頼は承認になりません。回答と承認は別記録にし、同じ発言に両方が明示されればそれぞれ記録します。同じ版・範囲が承認済みなら重複確認せず、上位指示・現在のユーザー指示と権限制約に従います。

大きな実装では目的、主要機能・画面と流れ、対象内外、構成・依存関係、段階分けの全体像を個別タスク着手前に提示・承認します。未解決事項は確定仕様・承認欄から分け、なしの場合も明記し、影響・選択肢/提案・必要な判断をまとめます。承認だけで実装必須判断を補完せず、その範囲は解決か明示的な除外/委任まで止めます。部分承認はその範囲だけ開始し、子タスクは親仕様版と承認範囲を引き継ぎ、単なる分割で取り直しません。

保存ONでは既存タスク仕様を正本に参照・版・提示証拠・UI非該当理由と、独立した承認欄の状態・対象版/範囲・ユーザー発言根拠を記録し、保存OFFでも会話内で同じ契約を守ります。承認待ちはplanned/承認pendingとし、ready移行、実装担当の受領、レビューで提示・承認・実装必須判断を確認します。振る舞い・UI・範囲・重要な設計判断を変える仕様変更は影響範囲を止め、関係資料を先に更新・再提示・再承認します。誤字等の意味を変えない修正は承認範囲を維持し差分を記録でき、範囲内の通常の検証・修正に毎回確認は要求しません。delegation/review/improvement_loop OFFでもactiveなら適用します。inactiveでは追加せず、純調査・仕様作成だけの依頼に本実装・コード委譲・Git工程は要求しません。Designer自動化は対象外ですが、UI実装前の視覚モックは必須です。これは指示による開始条件で、runtimeの機械的な実行阻止や新設定キー・状態schemaを追加しません。

未コミットの変更を勝手に捨てたり、stashしたりしません。新しいworktreeへ含める必要がある変更は、ユーザーが選んだチェックポイントを使います。Gitを使っていないプロジェクトは順次実行します。

修正・再レビューは２巡までとし、解決しない場合はメインへ判断を戻します。外部へのpush、PR作成、マージは別途依頼された範囲でのみ行います。

文献調査には候補探索と一次資料確認、コード変更には独立したリスク確認、Web画面の受入条件には実操作評価の手順を用意しています。該当する依頼の手順だけを読み、Web操作は利用可能なブラウザがある場合に実施します。これらは追加担当やブラウザ評価を自動起動しません。

Web検索・調査だけの依頼にも導入済みの入口から[出典規則](../../plugins/codex-harness/skills/harness/references/routing/web.md#webを参照した回答の出典)を適用します。Webを根拠にした主張の近くに実際の根拠ページへの説明的なMarkdownリンクを付け、一次資料を優先します。論文は確認できたタイトル・著者・年とDOIまたは出版社・arXiv等への直接リンクを示し、必要な閲覧範囲と推測を明記します。検索自体や、純粋な検索へのコード委譲・Git工程は要求しません。inactiveでは通常の作業へ戻り、上位指示とユーザー指定を優先します。ホストの引用UIを変更する機能ではなく、回答時の指示です。

## 記録とPC間の引継ぎ

`docs/harness/` にタスク仕様、主要ファイルへの案内、ADRを保存します。全フォルダへのREADME生成や、全会話のコピーは行いません。長い実行ログと計測値はPC内に保存します。

別PCへ移る前にコードとタスク記録を保存・同期し、新しいCodexタスクで対象タスクIDからの再開を依頼してください。起動中のエージェントやworktreeは同期されません。修正記憶は[同じ個人共有設定・安定ID・fresh read](improvement-loop.md#別pc別worktreeで再利用する)で再利用し、non-Gitは `.harness.json` も一緒に持ち運びます。長い作業では[早期compactの引継ぎ手順](../../plugins/codex-harness/skills/harness/references/early-compaction.md)を参照できます。独自の背景監視・compact API・会話削除はv1の対象外で、実行手段はホストが提供する正式な機能に依存します。

## CLIで記録を扱う

[補助CLIのコマンド](../../plugins/codex-harness/skills/harness/references/commands.md)はタスク作成・依存検証・worktree・計測を支援します。CLIパケットは `docs/harness/tasks/<id>.json` です。Markdownの仕様を重複生成する必要はなく、既存の仕様正本を参照して承認版・範囲・提示根拠を保ちます。レビュー判定・進捗の更新・統合は担当が行います。

dirtyなcheckoutではworktree作成が拒否される場合があります。現在の変更を勝手にstash/resetせず、同じcheckoutで直列に作業するか、必要な変更を利用者が選んだチェックポイントへ保存します。

## 計測の読み方

通常実行とハーネス実行を同じ開始状態のタスクで比較します。他作業との重複、利用枠のリセットをまたぐ記録、未取得の値は比較から除きます。アカウント全体の消費差分を正確なタスク費用とせず、トークン数を利用枠へ換算しません。長期的な改善や削減効果は未確認です。[計測契約](../../plugins/codex-harness/skills/harness/references/measurement.md)と[検証記録](../../VALIDATION.md)を参照してください。
