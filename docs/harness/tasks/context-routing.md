## 目的と確定方針

現在20,625 bytes/8,747文字のharness入口を、短い共通ルールと独立したYes/Noの読込判定へ整理する。判定は複数Yesが可能で、実装・制作・調査・Claude相談が重なる依頼を取りこぼさない。必要な概要から詳細へ進み、曖昧なら関連概要だけを読み、全資料を一括で読まない。

共通の権限・ユーザー指示優先・機能OFF・worker境界・実装前の承認条件・矛盾時の原資料確認は入口で判断できるよう残す。実装前説明/モック/承認、調整・委譲・独立レビュー・統合、Web出典、制作改善、設定の詳細、記録・再開等は条件付きの参照へ移す。既存各節から移動先への対応表を作り、規則を消したり適用範囲を変えたりしない。純相談・調査・アイデア出しに実装工程を追加しない。

## 利用者から見た振る舞い・入出力・異常時

- 起動指示→status→active時の短い入口→該当する手順という流れ。inactive・delegation/review/persistence/measurement/improvement_loopのOFF条件、旧設定互換性、モデル選択の既存契約を維持する。
- 子は割当範囲と必要な共通境界だけを受け取り、調整手順や再委譲を再起動しない。
- 同一版を既読かつ内容を保持している間は不要な再読を避ける。範囲・設定・役割・資料版・ユーザー指示が変わったら再判定し、要約等で内容を失った場合は必要箇所を再確認する。新たな永続キャッシュや自動スケジューラを追加しない。
- 図とエージェント向け判定表に同じ条件IDを用い、対応を検証できるようにする。図のためにエージェントへ大きな図表データを読ませない。
- 分岐や必要資料が不明・欠落なら、関連概要の確認または不足の報告を行い、規則を黙って省略しない。
- 入力は現在の依頼・作業段階・実効設定・担当範囲。出力は選択する資料と、測定したbytes/文字数/参照一覧。会話全体の使用トークン・利用枠・速度向上へ換算しない。
