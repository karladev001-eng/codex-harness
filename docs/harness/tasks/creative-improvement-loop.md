## 目的と対象外

UI・文書などの制作と修正を重ねることで、ユーザーの好みを根拠付きで記録し、次回に適用・評価・更新する。既存の指示ベースのハーネスに組み込み、常駐監視や新しい外部サービスは追加しない。ユーザーの美的嗜好は未取得であり捏造しない。自動ベンチマーク、モデル学習、公開・pushは対象外。

## 受入条件

1. インストールされる入口とSKILLが、コードに加えUI/文書の制作・修正・そのフィードバックからループへ到達する。純粋なクリエイティブ依頼には不要なコード委譲・Git工程を強制しない。コードを含む作業は既存の実装レビュー工程を維持。
2. 観察→仮説→適用→評価→更新を制作開始・修正・完了・次回開始に接続し、現在の指示を常に優先する。観察、候補、制作指針、試用結果を区別し、項目ID/根拠/明示か推測か/用途/日時/状態/履歴を記録可能な雛形を用意。
3. 単発修正は候補、明示的な継続希望は適用可、反復した独立の根拠で昇格。無反応・自分の評価・同一指摘の複製を支持に数えない。矛盾時は停止/範囲限定/訂正、重複統合、取消・忘却を扱う。探索依頼には作風を固定しない。
4. 個人の記録はインストール管理領域・共有Gitの外のホストローカルへ。statusで得るlocal_root配下のプロジェクト別領域を既定とし、共通好みを扱うなら明示的に範囲と優先順位を定義。未作成なら空から開始し、初回にプロフィール入力や許可を要求しない。委譲先には必要最小限の指針だけを渡し、親が記録を一元更新する。
5. active=falseでは追加処理なし。persistence=falseでは永続メモリを読み書きせず当該会話のみ。measurement=falseでも明示フィードバックと好みはpersistenceに従い扱えるが、集計・利用計測は保存しない。取得できない評価はunknown/null。改善効果は推測しない。
6. ユーザーが記憶を確認・訂正・忘却できる方法、破損・参照切れ・保存失敗時の継続/報告、同時更新の衝突回避、肥大化の抑制を定義。権限や安全規則を好みで上書きしない。
7. 配布物とインストール更新でも新しい参照/雛形が揃い、ユーザーメモリが更新・解除で消えないことを一時ホームで検証。既存テストと必要な動作テストを通す。Markdownの単なる文字列反復テストを増やさず、手動シナリオで嗜好遷移・フラグ・創作分岐も確認。
8. 既存未コミット変更を保持する。README/SPEC/検証記録が実際の動作と限界に一致し、レビューPASS後にローカル導入を更新して入口・参照の到達を確認する。実際の長期的な嗜好改善は未検証と明記。

## シナリオ確認の期待値

1. 「今回は前置きを削って」: 今回に適用し、次回の一般指針にしない。
2. 「今後、社内報告は結論から」: 用途付きの明示指針になる。
3. 同じ指摘の再開時読み直し: 新しい支持根拠として数えない。
4. 候補の試用後に無反応: unknownのままで昇格しない。
5. 「今回は物語風で」: 過去の結論優先指針より現在指示を優先。
6. 「この好みを忘れて」: 指針だけでなく再生成に使う観察・履歴も除去し、同一会話から再学習しない。
7. persistence=false: 永続記憶を読まず書かない。measurement=false: 明示的根拠は保持可、指標集計なし。
8. 候補段階の好み: 用途が合い今回限定でなければ暫定試用し、指針との違いを維持する。
