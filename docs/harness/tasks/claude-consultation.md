## 目的・対象範囲

会話で提示した「役割に応じてClaudeを外部サブエージェントとして使い、Codexが統合する」方針を実装する。対象役割はideator（アイデアマン）、consultant（コンサルタント）、critic（批評役）。今回、Claudeへの調査・実装委譲やファイル編集は追加しない。

## 入出力・異常時

Codexが目的、制約、評価軸、必要な文脈だけを構造化してCLIへ渡す。Claudeにはツールを与えず、隔離した作業ディレクトリで非対話実行し、回答をCodexへ返す。認証情報を取得・表示せず、既存Claudeログインを利用する。未導入、未認証、非対応CLI、異常応答、タイムアウトは理由を返し、成功扱いや無限再試行をしない。通常1回、追加質問は1回まで。回答は証拠・権限・ユーザー承認ではなく助言として評価する。

## 自動使用条件

- ideator: 企画、新しい使い方、改善案等の開かれたアイデア依頼で、複数の視点が有益。Codex案は初回に渡さず独立に発案する。
- consultant: 複数の有力案に判断上の懸念が残る方針・優先順位検討、移行・認証/権限・公開API互換性等の重要な設計判断、同じ問題を2回修正しても原因の見立てが更新できない停滞。
- critic: 重要な提案・設計を確定する前の弱点・見落とし確認、明示的な批評依頼。既存の独立コードレビューを置き換えない。
- 明示依頼を優先し、ユーザーが外部相談を止めた場合は呼ばない。単純な言い換え・定型変更・原因と対処が明確な修正では通常呼ばない。全役割の一律起動はしない。
- activeなharnessの親が判定。inactiveやdelegation=falseでは自動起動せず、明示的なClaude利用依頼は別扱い。HARNESS_WORKERは再起動しない。外部担当も同時実行枠に数える。保存OFF時は相談記録も永続保存しない。

## 受入条件

1. スキル名consult-claudeで3役の条件・入出力・統合・失敗時対応が明確で、自動選択が許可される。
2. harnessとbootstrapが純粋なアイデア/方針検討でも起動判定に到達し、既存の機能OFFとworkerの境界を守る。
3. ヘルパーはshell展開せず、入力以外をClaudeが読み書きできず、対話待ち・無限再試行・機密情報の表示をしない。正常/失敗/時間制限を意味のあるテストで検証する。
4. npm/build/plugin/恒久インストールでも参照先とヘルパーが欠けず、既存のインストール契約を壊さない。
5. 既存の未コミット変更を保持し、独立レビューと関連チェックを通す。実際の認証状態と実応答の確認可否を報告する。

6. CodexとClaudeの回答・資料・実装に不一致がある場合、Codexが元データ・一次資料へ戻り、版・日時・適用条件を確認する。多数決やAI同士の合意だけで正解としない。重要な未解消点は未確定として報告する。
7. 仕様HTMLの非ターミナル領域は明るい背景と暗い文字を明示し、OSのダークテーマ時も背景と文字が同時に暗くならない。
