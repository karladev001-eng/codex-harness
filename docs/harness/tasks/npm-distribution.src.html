npmだけで導入・更新する

npm-distribution · 仕様v2 · 実装承認待ち

全体像

Node.jsとnpmを用意したPCで、ホームから一つのコマンドを実行してハーネスを導入・更新する。手動clone・利用者側のビルド・tarball転送を不要にする。

各PCでGitHub Packagesへの初回認証 → npmがビルド済み配布版を取得 → 既存installで恒久導入 → 同じコマンドで更新。設定と記憶は保持し、編集済みの管理ファイルは上書きせず停止する。

実装順は配布物の生成 → 案内 → 一時registryからの導入/更新試験。配布先はGitHub Packages・非公開に確定。実registryへの送信は別工程。仕様・承認の正本。

仕様案

N1: 配布元でビルド済みのregistry配布物を作る。

stagingだけでpublish禁止フラグを外す。取得時のprepare/postinstallやAGENTS自動書込hookは追加しない。次版0.4.2を提案。registryはnpm.pkg.github.com、名前は@karladev001-eng/codex-harness。非公開の既存リポジトリに関連付ける。送信前にpackageの非公開状態・権限と版の未使用を確認する。

N2: 初回と更新を同じnpm execコマンドで行う。

同じ版はunchanged、新版は既存の所有管理に従って更新。@latestを具体版へ置換すれば版固定、installをuninstallへ置換すれば解除。取得したCLIはnpm cacheで動き、本体は恒久配置へコピーされる。cache削除後も利用できる。

N3: READMEから初回・更新・認証・解除を辿れるようにする。

単独スキルには同じ取得方式でauthoring installを使う。各PCでnpm loginとpackage権限を説明。401/403・404・通信失敗と、取得後の所有管理競合を分ける。tokenはチャットやコマンド引数へ貼らせない。

N4: 公開せずに実際のnpm経路を隔離検証する。

Node/npm/OSの実行版を記録し、他OS未実行は明記。製品画面の変更はないためコマンドを展示する。既存package/install試験を再利用する。

対象外: 実registry配布・公開設定・push・ライセンス変更・実PC導入・Chrome/Raycast登録・自動更新サービス。

現在の依頼は仕様作成として扱う。過去の承認やpush指示は新しい配布工程へ流用しない。

受入条件

  1. clone/build/手動転送なしでpackage.jsonのない場所から導入・更新できる（N1/N2/N4）。
  2. 古いcacheから新版取得、版固定、同版再実行、解除が動く（N2/N4）。
  3. 設定/記憶/無関係AGENTSを保持し、失敗や編集済み競合で既存導入を壊さない（N2/N3/N4）。
  4. 配布元でのみビルドし、秘密/実状態/内部実験と取得時自動hookを配布しない（N1）。
  5. 初回/更新/確認/解除/認証を案内し、配布前のコマンドを利用可能と書かない（N3）。
  6. 実配布や実環境変更を行わず、未検証を明示する（全体）。
