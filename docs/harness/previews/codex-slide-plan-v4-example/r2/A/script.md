# バッチ処理の改善案を、平均時間から考える

Deck: batch-comparison / revision: r2

## 1. S01 — まとめて処理する時間を短くする

### S01-P01

今日は、バッチ処理の改善案を、処理にかかる時間から比べます。バッチ処理とは、データを一件ずつ操作する代わりに、まとめて処理することです。開発者と非技術部門の皆さんが同じ数字を読めるように、まず比較の前提をそろえます。資料の値は、同じPCで現行と改善案をそれぞれ3回測ったという設定の、演習用の仮想値です。実運用で測った結果ではありません。今日は平均時間の差と、その差をどこまで判断材料にできるかを共有します。

出典: brief, measurements

つなぎ: 条件をそろえて、次に平均時間を見ます。

## 2. S02 — 平均40秒から25秒へ、15秒短縮

### S02-P01

比較の条件が分かったので、平均時間の差を見てみましょう。現行は3回の平均が40秒、改善案は25秒でした。つまり、今回の仮想測定では、改善案が平均で15秒短くなっています。現行の40秒を基準に計算すると、37.5パーセントの短縮です。左の横棒と右の表は同じ平均値を示し、表には各回の範囲も添えています。現行の値は38秒から42秒、改善案は24秒から26秒でした。短縮という表現は、あくまでこの演習用の仮想値を比較した結果です。実運用でも15秒短くなるとは確定できません。この違いを押さえたうえで、次に実運用でそろえる条件を整理します。

出典: measurements, summary

つなぎ: この差を踏まえて、実運用で何を確かめるか整理します。

## 3. S03 — 次は実運用の条件で確かめる

### S03-P01

まとめると、今回の仮想測定では、平均時間が40秒から25秒になり、15秒の差がありました。これは改善案を確かめるための比較例として使います。実運用の効果を判断するには、同じ入力データ量を使い、どこからどこまでの時間を測るかをそろえる必要があります。そのうえで複数回の値を残し、平均だけでなく値のばらつきも見ましょう。今回の資料には実運用の入力や測定範囲がないため、その効果は未検証です。この平均時間の読み方を共通の土台にして、次の実測でそろえる条件を相談できればと思います。

出典: summary, next-proposal

つなぎ: この比較を共通の土台として、実測の条件を相談します。
